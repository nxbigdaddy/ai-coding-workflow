# 快速入门：有了想法后，第一步做什么？

## 结论

**第一步不是让 AI 写代码，而是把想法变成「可约束、可验证的规格（Spec）」。**

## 为什么要先写 Spec？

AI 编程出问题的根源，往往不是模型能力，而是输入约束不够：

| 问题 | 原因 |
|------|------|
| 架构混乱、范围膨胀 | 想法模糊，AI 自行脑补 |
| 代码看起来有但跑不起来 | 没有明确的完成标准 |
| 过度设计、改太多文件 | 没有「明确不做」的边界 |

Spec 是后续整套提示词体系的**源头输入**，Rules、Skills、任务提示都从这里派生。

## Spec 要回答什么？

| 维度 | 要写清楚什么 |
|------|-------------|
| **目标** | 解决谁的问题？核心价值一句话 |
| **范围** | MVP 包含什么、**明确不包含什么** |
| **完成标准** | 怎样算「做完了」？可演示的场景 |
| **技术约束** | 语言、框架、部署环境、已有系统对接 |
| **非功能要求** | 性能、安全、离线、多用户等 |
| **未知项** | 还不确定、需要先调研或试错的点 |

## 推荐行动顺序

1. **今天**：用 [Spec 模板](templates/spec.md) 把当前项目想法写出来（哪怕只有半页）
2. **讨论阶段**：审 Spec——范围是否过大、技术选型是否合理、验收是否可测
3. **执行阶段**：搭建 `.cursor/rules/`、任务模板，再开始第一个 MVP 模块

## 和直接让 AI 写代码的对比

| 做法 | 结果 |
|------|------|
| 有想法 → 立刻「帮我做一个 xxx」 | 容易半成品、架构漂移、难维护 |
| 有想法 → **先 Spec** → 再 Rules → 再分任务 | 输出更完整、可复现、可迭代 |
